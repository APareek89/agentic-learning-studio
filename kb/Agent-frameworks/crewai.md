## What it is

CrewAI is a Python framework for building AI automations around named agents, explicit tasks, tools, and orchestration modes. Its center of gravity is multi-agent work: a crew is a team of agents with role prompts and responsibilities, while a flow is a more procedural, event-driven workflow that can call crews or individual steps.

In lessons, CrewAI is useful because it makes the social shape of an agent system visible. Learners can see why a "researcher", "analyst", and "writer" are separate, what each is allowed to do, and how task outputs become context for later work.

## Why it exists / when to reach for it

Reach for CrewAI when the problem naturally decomposes into specialist responsibilities and the team wants a concise, readable description of that decomposition. It is especially approachable for demos, business automations, research-and-write pipelines, sales/recruiting workflows, and other cases where a few agents collaborate over documents, APIs, or domain tools.

Use flows when the system needs control points: branching, event handlers, state, single LLM calls, and deterministic code around agentic steps. Use crews when the system benefits from collaborative autonomy and task handoff.

## The moving parts

- Agent: a role, goal, backstory or instructions, model settings, memory options, delegation permissions, and tools.
- Task: a unit of work with a description, expected output, optional context, and assignment to an agent.
- Crew: the container that binds agents, tasks, process mode, memory, cache, planning, and kickoff inputs.
- Process: commonly sequential or hierarchical. Sequential runs tasks in order; hierarchical adds a manager-like coordinator.
- Flow: an event-driven orchestration class with start/listen/router-style control, typed state, and the ability to call crews as steps.
- Tooling and platform features: model connectors, knowledge sources, guardrails, observability, CLI scaffolding, and optional enterprise control-plane features.

## How it works

A typical CrewAI app starts with agent and task definitions, often generated by the CLI and stored in project files. At runtime, `kickoff` supplies inputs, the crew expands task prompts, agents call tools as needed, and each task result becomes material for downstream tasks. In a flow, normal Python code owns the route: one method starts, listeners react to state or prior results, routers branch, and crews can be invoked inside those methods.

The important teaching point is that CrewAI gives you two orchestration dials. Crews express who should collaborate and what they should produce. Flows express exactly when things happen and how state moves.

## When to use vs alternatives

Use CrewAI over LangGraph when readability and role/task modeling matter more than explicit graph state machines. Use LangGraph when resumability, deterministic transitions, checkpointing, and low-level state control are the main lesson.

Use CrewAI over OpenAI Agents SDK when you want framework-level multi-agent structure independent of a single provider's SDK style. Use OpenAI Agents SDK when OpenAI tools, tracing, sessions, guardrails, and handoffs are already the app's native runtime.

Use CrewAI over AutoGen/AG2 when tasks and process feel more natural than free-form agent conversations. Use AutoGen/AG2 when the lesson is specifically about conversational agents, user proxies, group chat, or human-in-the-loop message patterns.

## Failure modes & gotchas

Role prompts can create convincing theater without improving quality. Add extra agents only when they bring different tools, information, checks, or decision rights.

Costs and latency multiply quickly because each task can trigger multiple model calls and tool calls. Budget the workflow, not just the individual prompt.

Task boundaries need crisp expected outputs. Vague tasks lead to duplicated reasoning, circular handoffs, and weak final aggregation.

Flows are better for production control, but they also move responsibility back into application code. Handle retries, idempotency, secrets, tool permissions, and telemetry deliberately.

Check which features are open-source library features and which belong to CrewAI's hosted or enterprise product. Do not imply that a control-plane feature is available in a local OSS install without verifying it.

## Minimal code shape (pseudocode/short snippet you write)

```python
from crewai import Agent, Crew, Process, Task

researcher = Agent(role="Researcher", goal="Find grounded facts", tools=[search_kb])
writer = Agent(role="Writer", goal="Turn facts into a clear lesson")

research = Task(description="Collect key evidence for {topic}", agent=researcher)
draft = Task(description="Draft a learner-friendly explanation", agent=writer, context=[research])

crew = Crew(agents=[researcher, writer], tasks=[research, draft], process=Process.sequential)
lesson_notes = crew.kickoff(inputs={"topic": "agent memory"})
```

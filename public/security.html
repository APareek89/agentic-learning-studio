Security

Last updated: 25 June 2026

This page is provided for product transparency and is not legal advice. Formal legal review is still recommended before taking payments or scaling the service.

Wizbit / PrathibhaX is operated by Anand Pareek, an individual resident in India. This page describes the safeguards in place today and the improvements planned. Report a vulnerability or security concern to findkailash@gmail.com or via Report issue / complaint (category: “Security vulnerability”).

In place today

  • HTTPS everywhere — the app is served over TLS by our host (Render).
  • Security headers — applied via Helmet (e.g. frame, content-type, and referrer protections).
  • CORS lockdown — the API only accepts requests from our own origins; cross-origin access is restricted.
  • Authentication — handled by Supabase Auth; we never see your raw password.
  • Row-Level Security (RLS) — enabled on public database tables; client roles are denied direct access.
  • Server-side database access only — all data access flows through our server API, not directly from the browser.
  • Rate limits — per-IP limits protect the API and the complaint form from abuse.
  • Upload & repository caps — bounded file counts, sizes, and timeouts on uploads and repo imports.
  • Sandboxed lessons — generated lessons render inside a sandboxed iframe to isolate their inline scripts.
  • Local embeddings — uploaded content is embedded locally to ground lessons, minimising what leaves the server.

Known limitation: Content Security Policy

A strict Content-Security-Policy (CSP) is intentionally off today because generated lessons and the host page include inline JavaScript and CSS that a strict CSP would break. A stricter CSP using nonces is planned so inline scripts can be allow-listed individually.

Incident response

If a security incident occurs, we follow this flow:

  1. Detect the issue and confirm it’s real.
  2. Contain it to limit impact.
  3. Assess scope, data affected, and root cause.
  4. Notify affected users and authorities as legally required.
  5. Recover services to a known-good state.
  6. Preserve evidence for investigation and learning.

CERT-In posture

  • Clock synchronisation — systems sync to a reliable NTP source.
  • Secure logs — relevant logs are protected and retained for at least one year where applicable.
  • Incident reporting — covered cyber incidents are reported to CERT-In within 6 hours of detection where required.
  • Named security contact — findkailash@gmail.com.
